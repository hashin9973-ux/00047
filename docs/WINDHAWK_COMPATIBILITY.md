# Windhawk source compatibility audit

The audit tool helps estimate whether a C/C++ Windhawk mod can be ported to the current 00047 native-mod SDK. It does not execute the source or prove safety, ABI equivalence, or correct behavior.

## Run it

From the repository root:

```powershell
python tools/audit_windhawk_mod.py path\to\mod.cpp path\to\include
python tools/audit_windhawk_mod.py path\to\mod --json
python tools/audit_windhawk_mod.py path\to\mod --fail-on-unsupported
```

The scanner reads C/C++ source/header files, masks comments and ordinary/raw string literals, and reports the source locations where `Wh_*` identifiers occur. It excludes common build-output folders and the SDK compatibility header by default. Files over 2 MiB are skipped. `--fail-on-unsupported` returns exit code 2 when unsupported, unknown, lifecycle-adaptation, or warning findings exist, so it can be used in a porting checklist or CI. `--sarif` emits SARIF 2.1.0 with source locations and severity levels for code-scanning integrations. `--output` writes JSON/SARIF to a file without mixing diagnostic text into the machine-readable report. Paths inside the current working tree are emitted as repository-relative URIs; external files use `file:` URIs and are not suitable for repository-hosted code-scanning uploads without remapping. The report describes static compatibility findings and does not certify runtime safety or ABI compatibility.

## Supported subset

The source-level helpers also provide x64 function-hook registration/application through the bundled MinHook backend, instruction-length/disassembly reporting through the vendored diStorm decoder, and a bounded `Wh_HookSymbols` implementation that checks validated per-user file caches, existing Windhawk registry caches, and HTTPS online caches before resolving exact decorated/undecorated names through DbgHelp. The non-hook helpers cover `Wh_Log`, `Wh_GetIntSetting`, `Wh_GetStringSetting`, `Wh_FreeStringSetting`, scalar/string/binary local-storage APIs, `Wh_DeleteValue`, `Wh_GetModStoragePath`, dynamic-select option management, bounded HTTP(S) retrieval through `Wh_GetUrlContent` / `Wh_FreeUrlContent`, and bounded `Wh_FindFirstSymbol` / `Wh_FindNextSymbol` / `Wh_FindCloseSymbol` enumeration using Windows DbgHelp. `Wh_ModSettingsChanged` can be wired through a separate opt-in lifecycle adapter.

“Supported with limitations” deliberately does not mean binary compatibility. Storage is package-scoped; URL retrieval is bounded and rejects credential-bearing URLs; settings use 00047's manifest/settings files; and runtime callbacks are different. Symbol enumeration is a DbgHelp-backed snapshot capped at 100,000 records and approximately 4 million stored name characters, depends on matching PDB/symbol availability, and may perform network I/O when a symbol server is selected. DbgHelp state is process-global, so lookup can fail or conflict when another component initialized DbgHelp incompatibly. Use an empty `symbolServer` in tests to suppress remote retrieval. Review [NATIVE_MODS.md](NATIVE_MODS.md) before porting.

## Direct source import and umbrella header

The SDK supplies `windhawk_api.h`, the conventional include name used by Windhawk mods. It exposes the currently implemented source-level `Wh_*` helpers, hook declarations, and symbol helpers for C++ projects.

Run `python tools/import_windhawk_mod.py path\to\mod.cpp --output-dir path\to\mods` to generate a project from a single-file Windhawk source. The importer preserves the source and local quoted includes, maps exact allow-listed `@include` targets, creates a manifest and lifecycle wrapper, and translates a subset of flat settings defaults/options. Common `-l...`, `-D...`, and C++ standard flags are supported. It rejects wildcard/path target rules, `@exclude`, unsupported compiler flags, nested settings, and numeric arrays rather than silently altering behavior. Settings annotations such as `$showIf`, `$hideIf`, and `$format` are recorded as warnings but are not translated into the settings UI. Inspect `windhawk-import.json` and audit the source before enabling it. Import/build success does not certify equivalent runtime behavior.

## Nested setting groups

The importer accepts nested mapping groups and flattens leaf IDs to dotted paths (for example, `rendering.theme`) so existing Windhawk calls such as `Wh_GetStringSetting(L"rendering.theme")` retain their key. Group names are prefixed to labels, and group-level show/hide conditions are inherited by leaf settings. The settings editor remains a flat list rather than Windhawk's nested sub-form presentation. Object arrays/row templates are still rejected because they need per-row schema semantics.

## Flat setting visibility conditions

The source importer translates flat-setting `$showIf` and `$hideIf` maps into `showIf` and `hideIf` fields in the native-mod manifest. The settings editor updates visibility as values change, resolves dependencies recursively, retains hidden values when saving, and rejects unknown references, type mismatches, and dependency cycles. Conditions accept scalar values compatible with the referenced flat setting. It also preserves `$format` hints, with an HTML color picker for `colorRgb`, an alpha-aware color picker for `colorArgb`, and a range slider for `slider` settings that declare bounds. `filePath` and `folderPath` use the app's native open-file/folder dialogs. `hotkey` has basic virtual-key capture and stores Windhawk's lowercase modifier order, but webview events may not capture Windows-reserved shortcuts exactly. `fontFamily` uses a Windows GDI font-family list with a free-text fallback; it does not reproduce Windhawk's full font-picker presentation. Nested groups and object/array-scoped condition resolution still require manual porting.

## Compile-time metadata constants

Windhawk mods may use `WH_MOD_ID` and `WH_MOD_VERSION` as wide string-literal constants. The SDK's `windhawk_project_metadata.cmake` reads those values from the root `manifest.json`, generates `windhawk_mod_metadata.h`, and force-includes it for C and C++ compilation. The in-app source builder installs this helper through `CMAKE_PROJECT_INCLUDE`, so existing CMake projects do not need to know their target name. Generated C/C++ projects also include the helper explicitly when built outside the app. Existing explicit definitions are preserved. This fills a compile-time API gap; it does not make the native runtime binary-compatible with Windhawk.

## Implemented hook and symbol APIs: limitations

The SDK now provides source-level implementations of `Wh_SetFunctionHook`, `Wh_RemoveFunctionHook`, and `Wh_ApplyHookOperations` using the bundled x64 MinHook backend. Registration and removal are queued; the opt-in lifecycle adapter applies pending hooks after `Wh_ModInit` and removes tracked hooks after `Wh_ModBeforeUninit`. `Wh_Disasm` uses the vendored diStorm x64 decoder and Intel-syntax formatter, returning the decoded length, mnemonic, and operands instead of a mnemonic-only byte dump. Formatting can still differ from Windhawk's Zydis-based output for edge-case instructions. `Wh_HookSymbols` checks a bounded persistent local offset cache keyed by PDB GUID/age (when present) or PE timestamp/image size/name plus the selector set, then checks the existing Windhawk `HKLM\SOFTWARE\Windhawk\Engine\ModsWritable\<mod-id>\SymbolCache` value keyed by module PDB/PE identity. Registry data is treated as untrusted and offsets are validated before use; 00047 only mirrors compatible records back when that Windhawk key already exists and is writable, merging other valid symbol records rather than replacing them. If that key is absent or unwritable, the per-user cache remains the fallback. After those cache misses, it can use a 60-second per-user failure marker for repeated unresolved required symbols, plus the Windhawk `error:3` registry record format when the mod's existing Windhawk `SymbolCache` key is available. The registry record is scoped to process identity, mod version/library filename, and target image; 00047 uses target-process creation identity rather than Windhawk's manager-process identity, so this remains partial interoperability, not exact session-policy equivalence. a bounded 2.5-second per-mod/module named mutex lets concurrent 00047 target processes recheck local and registry caches before issuing duplicate online requests. It can then use Windhawk's HTTPS online-cache URL convention (explicit `onlineCacheUrl` or the default package-ID cache) with a 3.5-second request budget and at most one automatic redirect. All local and remote entries are validated against the loaded image and executable memory before use; validated remote entries are persisted locally. Error throttling is only partially compatible: 00047 can read/write the Windhawk `error:3` record format in an existing registry key, but scopes records to the target process and uses a fixed 60-second TTL rather than Windhawk's manager-process identity and startup/debug-logging policy. Hybrid-module handling and full hook-session semantics remain unimplemented.

These APIs are supported with limitations, not a claim of full runtime equivalence. Each DLL has its own hook-operation queue, while a named per-process registry serializes target claims across independently linked mods. Hook creation, hook-apply batches, shutdown removal, and unload-quiescence scans now hold the shared registry mutex for the entire operation, preventing bundled MinHook instances from concurrently mutating backend state or suspending and patching threads. It rejects duplicate targets and conservatively rejects target addresses less than 10 bytes apart, covering overlapping entry patches from the bundled x64 MinHook backend (a 5-byte entry jump and optional 5-byte hot-patch area). The first successful claimant wins; compact but genuinely separate function entries can therefore be rejected conservatively. The registry also prevents unloading a module while another registered hook targets an address inside it. A successful unload-safety query marks the image as retiring before releasing the shared mutex; subsequent SDK hook claims into that image are refused, closing the query-to-unload race for cooperating SDK users. A newly initialized lifecycle at the same module base clears the marker. Stale markers for unloaded modules are pruned when another module enters the retirement path, preventing repeated reloads from filling the fixed registry. The backend is x64-only and expects a valid executable target address; this address-window policy does not coordinate arbitrary executable-memory patches or reproduce Windhawk's complete hook-session behavior. The ABI v2 `WmodCanUnloadV1` query is wired into the host's unload path. The hook backend disables/removes tracked hooks and checks shared-registry references, then suspends accessible target-process threads and repeats thread enumeration until a complete pass finds no newly discovered live threads. It checks each suspended thread's instruction pointer, Win32 start address, and ordinary stack words for references into the module before resuming only the suspension it added. The scan is bounded and fails closed when a stable thread set or reliable inspection cannot be obtained; if quiescence cannot be confirmed within the host timeout, the DLL is retained instead of forcibly unloaded. This protocol reduces thread-creation races but is not a universal proof for remote thread injection, externally queued callbacks, custom fibers, saved continuations, or other control-flow state not represented on inspected thread stacks. Treat hook-enabled mods as experimental and test in a disposable environment. The opt-in settings adapter also supports `BOOL Wh_ModSettingsChanged(BOOL* bReload)`. A successful callback that sets `*bReload = TRUE` exports a reload request; the host observes it on the next enabled-mod scan and performs shutdown, quiescence validation, unload, and a fresh load. If quiescence cannot be proven, the DLL remains mapped and the host retries on a later scan rather than forcing unload. Unknown API calls remain blockers. A passing source audit cannot certify ABI equivalence, mod behavior, or safety.

## Lifecycle migration

For non-hook mods that provide the usual init and shutdown callbacks, include the opt-in header `sdk/native-mod/windhawk_nonhook_adapter.h` in the mod translation unit and place the macro invocation after the callback definitions. The header maps `Wh_ModInit`, `Wh_ModAfterInit`, `Wh_ModBeforeUninit`, and `Wh_ModUninit` onto 00047's `WmodGetApiVersion`, `WmodInitializeV1`, and `WmodShutdownV1` ABI. Define `WMOD_BUILD_DLL`, include the adapter header after the callback definitions, and ensure the callback signatures match the adapter contract:

```cpp
WMOD_DEFINE_WINDHAWK_LIFECYCLE(
    Wh_ModInit,
    Wh_ModAfterInit,
    Wh_ModBeforeUninit,
    Wh_ModUninit
)
```

The adapter guards repeated initialization and shutdown, applies queued hooks after the init callback, and removes tracked hooks between the before-uninit and uninit callbacks. Callback ordering is mapped, but timing remains different; the adapter is not a Windhawk runtime. If a port has no implementation for a void callback, `wmod::windhawk_adapter::NoopCallback` can be supplied explicitly. Do not use the adapter to hide missing behavior. The mod must still be checked for unsupported APIs and manual lifecycle needs. Hook calls must be linked against the bundled SDK sources, and settings/storage calls must use the supported helpers. The shared registry rejects duplicate targets and conservatively rejects distinct target addresses less than 10 bytes apart; compact but separate functions can be rejected, and arbitrary executable-memory patches are not coordinated. Exact Zydis disassembly formatting remains a limitation.

Mods using either `void Wh_ModSettingsChanged(void)` or `BOOL Wh_ModSettingsChanged(BOOL* bReload)` can use `sdk/native-mod/windhawk_settings_changed_adapter.h` and `WMOD_DEFINE_WINDHAWK_LIFECYCLE_WITH_SETTINGS_CHANGED` instead of the basic lifecycle macro. It watches the mod package directory for changes to `settings.json` and invokes the callback on a dedicated worker thread, then stops and joins that thread before shutdown callbacks. Thread affinity differs from Windhawk: the callback must be thread-safe, brief, and not assume UI/shell-thread affinity. Initialization fails if the directory cannot be watched. For the `BOOL(BOOL* bReload)` variant, the callback's return value indicates whether settings handling succeeded; only a successful callback with `*bReload = TRUE` requests reload. The host polls that request during its next enabled-mod scan (normally within the five-second scan interval), then shuts down the module, verifies quiescence, unloads it, and maps a fresh image. The request remains set while a DLL is retained for safety so a later scan can retry. The static auditor marks this callback as adapter-available, not fully Windhawk-identical; callback thread affinity and timing still differ. Review the mod's assumptions about callback timing, exceptions, threading, and cleanup before enabling it in a shell process.

## Native DLL publisher trust

The 00047 application can optionally require Trusted Authenticode signatures for native mods. This policy is OFF by default. When enabled, load-time verification calls Windows `WinVerifyTrust` using cached certificate/revocation data only; missing or invalid trust data fails closed, and verification does not perform network retrieval. The UI exposes the policy switch, persists it, disables all installed packages that do not verify (including ones previously marked disabled), and records unload retries durably. Pending cleanup is retried during background scans and blocks re-enable or package replacement until safe unload succeeds. The loader never forces unload when hook quiescence is uncertain. Signed code is still native unsandboxed code and should be reviewed.

## CI

Run the audit-tool unit tests with the rest of the developer-tool tests:

```powershell
python -m unittest discover -s tools/tests -v
```
